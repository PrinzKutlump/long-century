# Long Century implementation strategy

Use the public Long Century repository for project continuity. The owner reviews and merges changes. Codex carries the queue while Claude is paused.

## Where work lives

| Question | Permanent record |
| --- | --- |
| What have we promised? | [Feature ledger](LEDGER.json). Keep the feature ID for the life of the feature, including after completion. Regenerate [LEDGER.md](LEDGER.md) from the JSON. |
| What precisely must be delivered? | A GitHub issue linked to the ledger row. Record the player outcome, acceptance checks, dependencies, and source when the work has a historical or asset basis. Split independently testable work into child issues and link them to the parent. |
| Who is working on it, and where should they resume? | [Claims board #1](https://github.com/PrinzKutlump/long-century/issues/1). Post issue, branch, affected files, and ownership. On pause, add last verified commit, tests, blocker, and next concrete action to the issue or PR. |
| What changed, and how was it proved? | The PR, linked to the issue and ledger ID. Keep test commands, results, device or seed, and the first remaining gap there. |
| What comes next? | The sequence below and [Master Plan](MASTER_PLAN.md). Use the issue and PR links for current status. The Ottoman source reconciliation has its own review in [PR #60](https://github.com/PrinzKutlump/long-century/pull/60). |

## Rules for finishing and resuming

1. **Capture requests before coding.** Link each new request to an existing ledger row or add a new one. Give it a ticket when it is actionable. Record any owner-directed change in priority on the affected work. Leave previous requests visible with their status.
2. **Pull the first unblocked ticket.** Read the open ledger and claims board at session start. Use one branch per ticket. Explain overlaps with open PRs before editing shared files or the century hash.
3. **Record research at the point of use.** For historical events, save the source, historical fact, eligibility conditions, alternative outcomes, and expected test in the issue or PR. Test eligible and ineligible worlds. For features, cite the actual institution, shipyard, asset, deposit or border change and explain any gameplay simplification. Keep asset rights evidence per item in the asset manifest once available. AI-generated drafts are optional inputs. Verify their claims and rights before incorporating them. Use permitted aggregates for restricted historical datasets.
4. **Attach evidence to the PR.** Demonstrate the requested behaviour through its normal game entry point. Include save/reload, relevant seeds, and mobile verification where the feature affects them. Presence checks protect code references. Behavioural tests establish the result. Record timing, save size and hash where required by the master plan.
5. **Keep pending work visible.** A PR awaiting review or failing a gate remains open. A partial delivery lists which acceptance checks or subtasks are still open. Mark a feature done on main when its evidence is available. Preserve completed ledger rows and their tests. If functionality is reduced or removed, record the owner-approved decision and the player-facing effect in the PR and ledger.
6. **Reconcile at the end of each work session.** Compare the ledger, current issues and PRs. Record landed work, unresolved failures and the next action. Put durable facts in GitHub so the next session can resume from the issue and branch.
